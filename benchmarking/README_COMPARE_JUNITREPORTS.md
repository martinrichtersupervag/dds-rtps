# DDS Interoperability Report Analyser

A Python toolset for analysing JUnit XML reports produced by DDS vendor interoperability
test suites (9×9 publish/subscribe matrix). Reports are grouped by metadata embedded in
their filenames, compared chronologically, and rendered as plain-text summaries or a
self-contained HTML dashboard.

---

## Requirements

- Python 3.9+  
- No external packages required

---

## Filename Format

All input files must follow the naming convention:

```
junit_interoperability_report-DDMMYYYY-HHmm-parNN-XXXXsec-RUNNER-runB.xml
```

| Field | Meaning | Example |
|-------|---------|---------|
| `DDMMYYYY` | Date (day-month-year) | `02102026` |
| `HHmm` | Start time (24h) | `2111` |
| `parNN` | Number of parallel test workers | `par16` |
| `XXXXsec` | Total suite duration in seconds | `4992sec` |
| `RUNNER` | `self-hosted` or `ubuntu` (GitHub-hosted); optional | `self-hosted` |
| `runB` | Test suite run (batch) number - identifies tests started together; optional | `run3` |

Example: `junit_interoperability_report-02102026-2111-par16-4992sec-self-hosted-run3.xml`

`RUNNER` and `runB` are optional, so older files without them are still accepted.

---

## Integration with `run_benchmark.sh`

[`run_benchmark.sh`](run_benchmark.sh) produces the files in this format and stores them in
`benchmarking/results/runB/` (B = batch number, assigned automatically as highest existing + 1,
or set with `--batch B`; runner is set with `--runner self-hosted|ubuntu`).
After the last run it automatically calls this tool on the files of the current batch only:

```bash
python compare_junit_reports.py --directory results/runB --batch B --explain-parallel --html
python compare_junit_reports.py --directory results/runB --batch B --compare-all --show-differences
```

Outputs are written next to the reports in `results/runB/`:
`explain_parallel-RUNNER-runB.{txt,html,log}` and `compare-RUNNER-runB.log`.


## Quick Start

```powershell
# Compare the two newest XML files
python compare_junit_reports.py

# Full analysis: compare all reports chronologically + generate HTML dashboard
python compare_junit_reports.py --compare-all --show-differences --html

# Parallel-group analysis with HTML dashboard
python compare_junit_reports.py --explain-parallel --html
```

## CLI Reference

| Flag | Description |
|------|-------------|
| `first second` | Compare two specific XML files |
| `--compare-all` | Compare every file with the next chronological one |
| `--explain-parallel` | Group files by `parNN`, show per-run-normalised stats |
| `--html` | Generate `report.html` alongside text output |
| `--simple` | Concise summary output |
| `--show-differences` | Two-sided diff of status changes |
| `--json` | Machine-readable JSON output |
| `--include-times` | Include testcase runtime comparisons |
| `--include-details` | Include verbose failure/error detail diffs |
| `--directory PATH` | Read XML files from a specific directory |
| `--batch B` | Use only reports of test suite run (batch) `B` (the `-runB` part of the filename) |
| `--name-tag TAG` | Suffix of `explain_parallel{TAG}.txt/.html` (default `-<runner>-run<B>` derived from `--batch`) |

|------|-------------|----------|

## How Each Output Is Computed

### `explain_{from}_{to}.txt` — Explanation Report

Generated by [`generate_explanation()`](file:///d:/prog/polis/compare_junit_reports/junit_compare/explain.py).

#### Flaky test classification

For a **series of comparisons** (`--compare-all`):

| Category | Rule |
|----------|------|
| Truly flaky | Test changed status in **≥ 3** consecutive pair comparisons |
| Partially flaky | Test changed status in **exactly 2** consecutive pair comparisons |

For a **single comparison** (two files):

| Category | Rule |
|----------|------|
| Truly flaky | Status changed between `{passed, failure, error}` |
| Partially flaky | Status changed involving `skipped` |

#### Permanent pass / fail / mixed

Computed from `summarize_test_statuses()` which aggregates counts across **all** XML files:

| Metric | Formula |
|--------|---------|
| Always-passing | `unique_tests − len(tests_with_any_failure)` |
| Always-failing | `passed == 0` AND `(failure > 0 OR error > 0)` |
| Mixed | `passed > 0` AND `(failure > 0 OR error > 0)` |

---

### `explain_parallel.txt` — Parallel-Group Report

Generated by [`generate_explain_parallel()`](file:///d:/prog/polis/compare_junit_reports/junit_compare/explain.py) via [`build_explain_parallel_report()`](file:///d:/prog/polis/compare_junit_reports/junit_compare/analyzer.py).

#### Grouping

Files are grouped by the `parNN` value in the filename.  
Each group is analysed independently.

#### Normalisation

All raw counts are divided by **`run_count`** (= number of XML files in the group)
to produce a *per-run average*:

```
avg_failures_per_run = total_raw_failures / run_count
```

#### Flaky detection (within a group)

A test is **flaky** in a parallel group when, across all files in that group:

```
passed > 0  AND  (failure + error) > 0
```

This means the test produced different outcomes in different runs at the same parallelism level.

The **fail rate** for each flaky test is:

```
fail_rate = fail_count / (pass_count + fail_count) × 100 %
```

#### Publisher / Subscriber breakdown

Test labels have the format:

```
{publisher}---{subscriber} / {test_suite} / {test_name} [{params}]
```

The publisher and subscriber are extracted with:

```python
re.match(r"\s*([^-]+-[^-]+)---([^-]+-[^\s]+)\s+/", label)
```

Failures (and flaky failures) are then summed per publisher and per subscriber independently.

#### QoS / Feature breakdown

The feature name is extracted from the test suite name:

```python
re.search(r"/ rtps_test_suite_\d+_Test_([A-Za-z0-9]+)_\d+", label)
```

Examples: `Durability`, `CoherentSets`, `Ownership`, `Reliability`, `Lifespan`.

### `report.html` — HTML Dashboard

Generated by [`generate_html_report()`](file:///d:/prog/polis/compare_junit_reports/junit_compare/html_report.py).

- **One tab per parallel group** — shows flaky analysis, QoS breakdown, publisher/subscriber tables with horizontal bar charts.
- **Run Comparisons tab** — (when `--compare-all --html`) shows the run-to-run diff table and failure frequency.
- Self-contained: no external dependencies at runtime, single `.html` file.

## Repeated-Change Detection (`--compare-all`)

Computed by [`_repeated_change_tests()`](file:///d:/prog/polis/compare_junit_reports/junit_compare/analyzer.py):

For each consecutive pair `(Rᵢ, Rᵢ₊₁)`, every test whose **status** changed is counted.  
Tests with a count **> 1** are reported — these changed status in more than one pair, indicating instability over time.

---

## Failure Frequency (`summarize_test_statuses`)

Aggregates `passed / failure / error / skipped` counts for every unique test label across **all** supplied XML files.  
Returns only tests that failed or errored at least once, sorted by total failure count descending.

`summarize_all_statuses` is the same but includes always-passing tests — used for flaky detection.
